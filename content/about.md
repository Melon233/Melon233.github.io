## 这个站是做什么的

你好，我是 **Chino**。这里是我的技术笔记本。

我不是专业写博客的人，建这个站的原因很朴素：**学东西的时候记不住，踩过的坑下次还会再踩一遍**。以前笔记散落在各种本地文件和聊天记录里，找不回来。放到网上之后，至少有了三个好处：

1. **能搜**——自己的东西也得能搜到才有用。
2. **能被将来的自己读到**——写得清楚一点，半年后的我看得懂。
3. **顺便帮到别人**——如果我踩的坑你也踩了，那这篇就没白写。

内容主要围绕编程、工具链和各种折腾过程。不追求体系完整，更像是**公开的草稿本**：想到什么写什么，写错的地方以后回来改。

> 如果某篇文章帮到了你，那挺好的。如果没有，也不必勉强读。

## 为什么是这种形态

这个站**没有任何后端**——没有数据库、没有服务器程序、没有登录。它就是一堆预先编译好的 HTML 文件，托管在 GitHub Pages 的 CDN 上。

这样做的好处很直接：

- **零成本**——GitHub Pages 免费，不需要买服务器。
- **零运维**——没有进程要盯，没有数据库要备份，不会因为机器挂了而打不开。
- **极快**——用户请求时服务器只是把现成的文件发回去，不执行任何代码。

代价是失去了动态能力：**不能有评论、不能有登录、不能实时生成内容**。对这个站来说，这些都是不需要的东西，所以这笔交易很划算。

## 它是怎么搭起来的

技术栈是 **Hugo + PaperMod + GitHub Actions**，三件套各司其职。

### 核心原理：静态站点生成

传统的博客是**动态**的，每次有人访问，服务器都要跑一遍程序、查一次数据库、现场拼出 HTML：

```text
用户请求 → 服务器执行 PHP/Node → 查询数据库 → 渲染 HTML → 返回
```

而 Hugo 属于**静态站点生成器**，它只在**我构建的那一刻**运行一次：

```text
我写 Markdown → Hugo 一次性编译成 .html → 推到 CDN
用户请求 → 直接返回现成的 .html（不跑任何程序）
```

**关键推论**：Hugo 在用户访问时根本不存在。这就是为什么单靠 GitHub Pages 就能托管——服务器只需要发文件，不需要执行代码。

### 为什么选 Hugo

对比过几个方案后选了 Hugo，主要三点：

1. **构建极快**——这个站全量构建只要 **30 毫秒左右**。因为快，所以它干脆每次都重建整站，不需要维护复杂的增量依赖。
2. **单文件二进制**——不需要装 Go、Ruby 或 Node，一个可执行文件就能跑。省掉了大量环境配置的麻烦。
3. **GitHub Pages 原生友好**——配好 Actions 后，`git push` 就自动发布。

它快的原因也挺有意思：Go 编译成原生二进制（没有解释器启动开销）、页面渲染并行分发到多核、不依赖数据库或 npm 依赖树。

### 三层分工

| 组件 | 负责什么 |
|---|---|
| **Hugo** | 把 Markdown + 模板编译成静态 HTML |
| **PaperMod** | 提供模板（决定页面长什么样），以 git submodule 引入 |
| **GitHub Actions** | 每次 push 后自动构建并部署到 Pages |

### 一次写作的完整流程

```bash
# 1. 新建文章
hugo new content posts/my-new-post.md

# 2. 本地预览（实时热重载）
hugo server --buildDrafts
#    打开 http://localhost:1313 看效果

# 3. 发布
git add .
git commit -m "post: 新增文章"
git push
#    Actions 自动构建，一两分钟后线上更新
```

## 站点结构

```text
my-blog/
├── content/
│   ├── posts/              # 所有文章（Markdown）
│   ├── about.md            # 本页
│   ├── archives.md         # 归档页
│   └── search.md           # 搜索页
├── assets/css/extended/    # 自定义样式（自动加载，不覆盖主题）
├── layouts/_partials/      # 覆盖主题的局部模板
├── static/                 # 图片等静态资源，原样拷贝
├── themes/PaperMod/        # 主题（git submodule）
├── hugo.yaml               # 全局配置
└── .github/workflows/      # 自动部署脚本
```

## 几个技术细节

这些是搭建过程中真正花时间的地方，记下来免得以后忘：

**搜索是前端实现的。** 静态站没有后端，所以 Hugo 在构建时把所有文章导出成 `index.json`，浏览器下载后用 Fuse.js 在本地搜索。这就是为什么配置里有 `outputs: home: [HTML, RSS, JSON]`。

**自定义样式不碰主题源码。** 任何放在 `assets/css/extended/` 下的 CSS 会被自动加载并追加到主题样式之后。Hugo 的查找顺序是「项目根优先于主题」，所以同名文件会覆盖主题的——定制和主题升级因此互不干扰。

**CSS 有内容指纹，favicon 没有。** Hugo 会给样式表文件名加上内容哈希，内容一变 URL 就变，缓存自然失效。而 `static/` 里的文件是原样拷贝、不经管道，所以 favicon 这类文件改完必须手动强刷。

**页脚覆盖了主题模板。** 因为 PaperMod 硬编码了 "Powered by" 署名且没有配置开关，只能复制一份 `footer.html` 到 `layouts/` 里改。代价是这个文件不再跟随主题升级，需要手动同步。

**注意 `baseURL` 必须写对。** 它用来生成全站绝对 URL，写错会导致所有 CSS 和图片 404。这是 Hugo + Pages 最常见的翻车点。

**仓库是公开的。** 免费账号用 GitHub Pages 必须公开仓库，所以**不要往这里提交密钥或私人内容**。`draft: true` 只是不渲染，文件仍然在仓库里。
